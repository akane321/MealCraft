# 交接说明：MealCraft 食谱/食材数据库

> **历史交接文档（2026-09-11）。** 这里的第一步到第四步已经完成：全量运行、schema v1 冻结、
> v1 与 v1.1 release 已发布在 `data/release/`。复核规则后来由 ADR-0024 改为"agent 或规则
> 解决并记录证据、人工事后抽查"。现行做法看 `README.md`、`docs/enrichment-work-package.md`
> 和 `docs/sources-and-licenses.md`；本文保留作为当时的背景。

这份文档写给**从零接手这项工作的人**。它不重复仓库里已有的文档，只说三件事：
现在是什么状态、接下来做什么、做完怎么交回。

先读这一页，再按需读 `docs/` 下的其他文档。

---

## 1. 这是什么

MealCraft 需要一个**可被规划器信任的**食谱与食材目录。当前产品里只有 30 道菜谱、
34 种食材，这个规模撑不起评价：想写"麸质过敏"的测试场景时只有 10 道菜含麸质，
想写"30 分钟以内"时只有 10 道菜达标。**目录太小，很多约束根本测不出东西。**

这个工程从 RecipeNLG（164 万条公开食谱）里抽样、解析、归一化，目标是产出几千条
**规划器可用**的菜谱。

"可用"有明确定义，四个条件缺一不可：

| 条件 | 为什么必须 |
|---|---|
| 每个食材都映射到规范 ID | 不映射就无法判断过敏原、无法匹配商品 |
| 每个食材都有数量 | 没有数量无法算用量和成本 |
| 单位可换算 | `1 bottle` 无法换算成克 |
| **有份量（serves N）** | 没有份量无法按人数缩放，营养也算不出来 |

## 3. 一个会改变你优先级的发现

接手前请先理解这一条，否则容易把时间花错地方。

**复核不是产出菜谱数量的瓶颈，份量才是。**

我算过"只复核卡住可用菜谱的那些食材"的收益：

| 复核食材数 | 可用菜谱总数 |
|---:|---:|
| 0 | 866 |
| 100 | 1,070 |
| 200 | 1,166 |
| 400 | 1,319 |

复核 200 个食材只多 300 条菜谱。而**把抽样从 85,000 提到全量 164 万，可用菜谱约
16,700 条**——不需要任何人工，只需要约 55 分钟机器时间。

原因是：食材映射覆盖率已经有 79%，而份量抽取率只有 9.7%。**9.7% 是那个把 8,310
砍到 866 的乘数。**

### 份量为什么提不上去

我检查过实际文本，"serve" / "make" 绝大多数是假阳性：

```
"If desired, serve over rice. Serves 4."     ← 只有后半句是份量
"Add water to make 2 cups."                   ← 不是份量
"Makes about 24 pieces."                      ← 产出块数，不是餐份
```

放宽正则会**编造错误份量**。而错误份量会静默地缩放每一个食材用量和每一个营养值——
不报错，只是全错。所以 9.7% 是诚实的上限，**不要试图靠放宽匹配提高它**。

### 那复核还要不要做

**要，但目的不是数量，是正确性。**

映射错了 → 过敏原标注错了 → 用户靠它避险。生杏仁和杏仁酱营养差一倍。
**这两类错误都不会报错**，只会静默地给出危险的建议。

所以复核的范围应该是：**实际出现在可用菜谱里的食材**，而不是队列里全部 15,785 个候选。

## 4. 接下来做什么（建议顺序）

### 第一步 · 扩样到全量（机器做，约 55 分钟）

```powershell
python -c "import sys; sys.path.insert(0,'src'); from mealcraft_data.cli import main; sys.argv=['x','run','--input','data/raw/recipenlg/full_dataset.csv','--sample-size','1643098','--seed','5105','--source-filter','Gathered','--review-limit','400']; main()"
```

会产出约 8GB 中间文件，确认磁盘够。跑完看 `reports/latest.md`。

> 你需要先自己去 RecipeNLG 官网接受条款并下载 `full_dataset.csv`，放进
> `data/raw/recipenlg/`。**这个文件不在压缩包里，也永远不要提交 Git**——许可只允许
> 非商业研究用途。详见 `docs/sources-and-licenses.md`。

### 第二步 · 生成按价值排序的复核队列（机器做，几分钟）

```powershell
python build_priority_queue.py
```

这个脚本是我加的，不在原工程里。它和管道自带的队列不同：

- **管道自带队列**按"问题类型"排序，第一行是 `empty_after_parsing`——像 `"1 cup"`
  这种解析失败的碎片，复核它只修好一行，而且答案通常是"这是垃圾"
- **这个脚本**按"复核它能解锁多少条菜谱"排序，并输出收益曲线，让你知道停在某处的代价

### 第三步 · 人工复核（人做，这是你的主要工作）

两个**不同**的任务，先做 A 再做 B：

**任务 A · 食材映射** —— `data/review/ingredient_priority_queue.csv`

判断"这段原文对应哪个规范食材"。例如：

```
原文: "1/2 (8 oz.) bottle Italian salad dressing"
问题: 这是什么食材？单位 bottle 怎么处理？
```

**任务 B · 营养匹配** —— `data/review/usda_foundation_candidates.csv`

判断"这个规范食材用 USDA 哪条营养数据"。例如：

| 食材 | 排名 | USDA 条目 | 相似度 |
|---|---|---|---|
| `almond` | 1 | Nuts, almonds, whole, raw | 0.71 |
| `almond` | 2 | Almond butter, creamy | 0.59 |
| `almond` | 3 | Nuts, almonds, dry roasted, with salt added | 0.58 |

正确答案是第 1 个。第 3 个加了盐，钠含量完全不同；第 2 个是杏仁酱，根本不是同一种
东西。**相似度 0.71 不高，靠猜是不行的**——这就是为什么必须人来做。

判断标准和填写方式见 `docs/review-guide.md`（已有，写得很清楚），重点是：

> `rank=1` 不能直接视为正确映射。字符串相似度只负责缩小人工搜索范围；审核者必须
> 确认食材形态、生熟状态、是否带皮/带骨以及营养基准。

**每一行都要填 `review_decision`，不确定就填 `reject` 并写明理由。留空等于没做。**

### 第四步 · 把复核结果写回规则

见 `docs/team-workflow.md` 的「改进归一化规则」一节。简单说：通用别名加进
`config/ingredient_aliases.csv`，通用单位加进 `config/units.csv`，然后重跑管道。

**不要直接改 `data/curated/` 里的产出**——那是生成物，重跑就没了。

## 5. 做完之后交回什么

交回这五样，缺一样我这边接不上：

1. **`data/review/` 整个目录** —— 填好 `review_decision` 的所有 CSV
2. **`config/ingredient_aliases.csv` 和 `config/units.csv`** —— 你补充过的规则
3. **`reports/latest.md` 和 `run_manifest.json`** —— 最后一次运行的质量报告与参数哈希
4. **`data/curated/*.jsonl`** —— 如果文件太大，只给我筛选后"四条件全满足"的那部分即可
5. **一句话说明**：这次跑的抽样量、seed、复核了多少条、哪些是你不确定的

第 5 条最重要。**不确定的地方要说出来**，我会把它标成 `needs_data` 而不是当成事实。

## 6. 三条红线

**不要提交 `data/raw/` 里的上游全量数据。** RecipeNLG 许可只允许非商业研究，且要求下载者
本人接受条款；2.3GB 也不该进 Git。版本化 release 是另一回事，见 `docs/sources-and-licenses.md`。

**不要不留证据地接受候选。** ADR-0024 允许 agent 或规则解决映射，但每条都要记录
选中的候选、来源、置信度和被否决的备选；错误的映射会把错误的营养传播到下游，而且不会报错。
过敏原仍只由确定性规则判定。

**不要给缺失的字段填猜测值。** 份量、营养、过敏原缺失时，正确做法是标记为缺失。
现在的管道就是这么做的（`status: "not_computed"`），请保持。

1. 读 `README.md` 和 `docs/data-dictionary.md`（约 20 分钟）
2. 跑 `python build_priority_queue.py`，看收益曲线（2 分钟）
3. 打开 `data/review/usda_foundation_candidates.csv`，找出**三个 rank 1 明显错误的例子**
   （约 20 分钟）

判断标准就清楚了。
