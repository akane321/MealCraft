## Implemented in this worktree

- The live parser path uses a capability-authorized model tool scheduler to route intent. The scheduler validates typed arguments, limits calls/steps, and keeps tool execution in local handlers.
- Planning preferences are separated from hard constraints and passed into planning scores: repeatable meal types, flavor boosts, more vegetables, and lighter meals.
- Food questions answer supported nutrition rankings from the catalog first; in explicitly selected OpenAI mode, a catalog miss may use required web search and attach URLs from provider citation annotations. Search failure or uncited output falls back to an explicit inability-to-verify response. Fixture mode makes no web call. This path is mock-tested; live search remains unverified.
- Structured external recipe intake maps ingredients through reviewed aliases, records uncertainty, checks household exclusions/allergens/dietary requirements and halal, and stores eligible recipes privately for that household.
- External recipe per-serving nutrition is recomputed from mapped gram weights and released ingredient nutrition-per-100-g data; extracted nutrition totals are ignored. Candidates with an ingredient lacking released nutrient data are blocked instead of storing unverified macro values.
- `/api/external-recipes/search-and-intake` now uses required Responses web search, extracts one typed candidate, requires the chosen URL to appear in response citations, and then invokes the existing mapping and admission flow.
- When external recipe admission is blocked or search/extraction is unavailable, the response explains the failure and offers up to three locally ranked catalog recipes that pass deterministic household safety and suitability filters. This fallback is covered by database-backed tests and makes no extra model or network call.
- `/api/ingredient-substitutions/suggest` asks the model for candidate names, then returns only catalog-mapped alternatives that pass household allergen, expanded exclusion and requested halal checks; it excludes the ingredient being replaced. `/review` supports validating a supplied candidate list with the same gate. Explicit replacement questions in chat use the same safety gate with the current conversation constraints, including reviewed English and Chinese ingredient aliases.
- The pre-plan confirmation card now displays extracted soft preferences and tells the household they can revise them in chat before planning.
- Halal is a fail-closed planning constraint across candidate generation and independent validation.
- Token usage and estimated API cost are recorded with model run metadata using dated model rates.
- The scope developer set contains 210 cases: 84 English, 84 Chinese, and 42 mixed. The reference-policy-only report is in `scope-reference-developer-2026-10-21.md` and its JSON companion.
- Expanded the constraint-understanding developer set to 162 English, Chinese, and mixed-language cases (57 English, 69 Chinese, 36 mixed). It covers household size, weekly/per-meal/per-person budgets, time, allergens, exclusions, dietary rules and halal, health/nutrition targets, pantry quantities and follow-ups, soft preferences, repetition, pricing, and medical boundaries. The deterministic fixture parser scores 100% exact case match, field precision/recall/F1, clarification accuracy, and medical-boundary accuracy; both English and Chinese score 100%. The case builder is `backend/scripts/build_constraint_understanding_dev_v1.py`; the report is `constraint-understanding-reference-dev-v1.json`. This remains a developer-set reference-parser result, **not a live-model result or held-out evidence**.
- The expanded cases exposed and fixed: nutrition values misread as household size; Chinese family-size phrasing; “serve N” and hyphenated time limits; weekly budgets; hyphenated low-sodium/low-sugar; chained ingredient exclusions; pantry quantities leaking to a second ingredient and milk aliases; quantity/unknown replies; Chinese vegetarian/dairy-free and soft-preference wording; “lighter” being misread as a flavor; set-like list ordering; and Chinese medical-boundary evaluation. Each parser behavior change has a regression test.
- Added a 20-case meal-shape-change developer set covering add/drop meals, dish-role changes, one-dish requests, and non-shape requests. The deterministic shape rules score 100% exact match, with zero false positives or negatives; English (9) and Chinese (9) both score 100%. See `meal-shape-change-reference-dev-v1.json`. This is rule-based developer evidence, not live-model or held-out evidence.
- Added an offline ingredient retrieval benchmark over 122 accepted/rejected developer terms (120 positive, 2 no-match), including English/local and 59 Chinese terms. With reviewed exact aliases plus the spelling fallback, Recall@1 is 97.5% and Recall@4 is 100%; Chinese Recall@4 is 100%. Low-confidence spelling results are filtered, so neither no-match case receives random suggestions. The report is `ingredient-retrieval-spelling-dev-v1.json`. This measures the local alias/spelling baseline only; semantic embedding retrieval is not measured without query embeddings.
